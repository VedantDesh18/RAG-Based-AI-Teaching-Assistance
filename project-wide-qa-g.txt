## 4. Diagnose existing and recurring failures

Search the repository and logs for these known symptoms, then determine whether they still occur:

- `422 Unprocessable Content` during file upload.
- `OPTIONS 405 Method Not Allowed`.
- `GET /` returning 404.
- `File reconstruction error` or CAS client errors.
- `mkl_malloc: failed to allocate memory`.
- Videos with a missing database `file_path`.
- Local-video chat input remaining disabled.
- Missing or stale chunk counts.
- Duplicate video records or duplicate chunks.
- Gemini API authentication, quota, timeout, and model errors.
- Slow retrieval or delayed first-token generation.

For every failure:
1. Reproduce it where possible.
2. Capture the relevant request, response body, logs, and traceback.
3. Identify the root cause from evidence.
4. Fix the cause rather than suppressing the error.
5. Add a regression test.
6. Verify the fix with a new test run.

A root URL returning 404 is not automatically a functional failure if the application intentionally exposes its API under `/api`. Do not confuse unrelated warnings with the actual cause of an upload or chat failure.

## 6. Improve answer quality and query speed

Optimize the existing RAG pipeline before introducing additional services or replacing working components.

### A. Measure first
Instrument these stages independently:

- Frontend request to backend.
- Query preprocessing.
- Query embedding.
- Vector retrieval.
- Optional reranking.
- Prompt construction.
- Time to first generated token.
- Total generation time.
- Total end-to-end response time.

Record timings using a monotonic timer. Use structured logs and never log API keys or unnecessary private transcript content.

### B. Improve retrieval relevance
- Inspect current chunk sizes, overlap, metadata, and embedding model.
- Verify that metadata filters use the correct video ID and search scope.
- Tune `top_k` using a small representative evaluation dataset rather than guessing.
- Avoid retrieving too many irrelevant chunks.
- Deduplicate overlapping or repeated retrieved chunks.
- Consider hybrid lexical and vector retrieval if it improves measured results.
- Consider a lightweight reranker only if its accuracy improvement justifies its latency and memory cost.
- Keep timestamps and source metadata intact throughout the pipeline.
- Ensure that relevant evidence from multiple chunks can be combined.
- Return a transparent insufficient-evidence response when retrieval does not support an answer.

Do not change the embedding model while continuing to query old vectors as if they were compatible. If a different embedding model is justified, use a separate versioned collection and a controlled re-embedding plan. Do not re-embed the existing database without approval.

### C. Reduce answer-generation latency
- Keep the system prompt concise without removing grounding or citation requirements.
- Limit retrieved context to relevant evidence.
- Set reasonable output-token limits according to answer type.
- Avoid unnecessary sequential model calls.
- Stream generated answers to the frontend if supported by the existing architecture.
- Reuse initialized clients and models rather than repeatedly loading them.
- Use caching for deterministic, reusable preprocessing or embeddings when safe.
- Cache retrieval results only when the cache key accounts for the question, selected video, filters, and relevant data version.
- Do not return stale cached answers after video data changes.
- Use bounded concurrency, connection reuse, and sensible timeouts.
- Handle retries only for transient failures, with backoff and a retry limit.
- Avoid sending large transcripts or the entire database to Gemini for every query.

### D. Preserve answer correctness
Speed improvements must not come at the expense of factual grounding.

Maintain:
- Answers based on retrieved transcript evidence.
- Accurate timestamps.
- Correct video references.
- Clear uncertainty when evidence is missing.
- Consistent response formatting.
- Existing streaming and frontend compatibility.

Do not claim a speed improvement without before-and-after measurements on the same representative queries.
